# Legacy Firmware V0 — Findings

```text
identifier: LEGACY_FIRMWARE_V0
role: historical/prototype evidence only, not production acquisition firmware
exact source archive: UNAVAILABLE_IN_REPOSITORY
```

The sketch itself was supplied outside this repository during the T004 conversation and is not a
tracked file here. No source code is reconstructed from memory in this document. Everything below
is recorded as an `OBSERVED_FROM_SOURCE` fact about that external sketch, not as a verified
property of any specific physical board. None of it satisfies `HW01` bench verification; the
`VERIFICATION_REQUIRED` registry in `contracts/HARDWARE_DATA_CONTRACT_V1.md` is unchanged by this
document.

## MAX30102 initialization observed

Source calls approximately:

```cpp
particleSensor.setup(100, 4, 2, 100, 411, 4096);
```

Status: `OBSERVED_LIBRARY_CALL_ARGUMENTS`. The exact semantic meaning of each argument (LED
brightness, sample average, LED mode, sample rate, pulse width, ADC range) is not assumed here; it
requires verification against the actual library version and hardware. MAX30102 register
configuration and achieved sample rate remain `VERIFICATION_REQUIRED`.

## ECG behavior observed

- Firmware initializes the ECG reading to a fallback value around `2048` before/without a valid
  lead-connected reading.
- Firmware checks lead-off detection pins (`LO+`/`LO-`).
- `analogRead()` is called only when leads are reported connected; otherwise the fallback value is
  transmitted/displayed.

**Consequence**: `2048` must never be interpreted as a physiological ECG reading. It is a firmware
fallback/idle value. A future canonical sample representation needs an explicit lead-off/validity
state (`ecg_quality = UNUSABLE` or equivalent), not a numeric sentinel comparison. Achieved ECG
sampling rate, timer jitter, and analog front-end gain/filtering remain `VERIFICATION_REQUIRED`.

## Pulse rate observed

Firmware computes beat timing from the MAX30102 **IR** signal using a `checkForBeat()`-style
routine. The transmitted field named `bpm` in this legacy firmware is therefore closer to a
**PPG-derived pulse-rate estimate** than an ECG-derived heart rate.

**Consequence**: this legacy `bpm` field must not be mapped to the canonical `hr_ecg_bpm` field in
`contracts/sample_schema_v1.json`. If a future adapter maps it at all, the correct canonical
destination candidate is `pr_ppg_bpm`, and that mapping itself remains unverified pending T004-class
bench work on the actual connected hardware.

## SpO2 observed

The existing code uses a simple red/IR ratio heuristic approximately of the form:

```text
110 - 25 * (red / IR)
```

with some clipping/thresholding.

Status: `PROTOTYPE_HEURISTIC_ONLY`. This is explicitly **not**:

- medically validated SpO2;
- a laboratory reference measurement;
- the final project SpO2 algorithm;
- a calibrated measurement of any kind.

SpO2 derivation algorithm and provenance remain `VERIFICATION_REQUIRED` in the hardware contract.

## Network behavior observed

The existing WebSocket payload contains approximately only:

```json
{ "bpm": "...", "spo2": "...", "ecg": "..." }
```

sent roughly every 50 ms.

**Consequence**: this transport does **not** satisfy the canonical high-rate waveform contract in
`contracts/sample_schema_v1.json`. It also lacks, at minimum:

```text
participant_id
session_id
device_id
firmware_version
sensor_config_hash
sample_index
timestamp_us
raw red PPG
raw IR PPG
quality
sequence number
packet integrity
algorithm provenance
```

Transport loss characteristics, real packet timing, real synchronization behavior, and real
throughput all remain `VERIFICATION_REQUIRED`.

## BLE observed

The existing firmware uses the standard Bluetooth Heart Rate Service / Heart Rate Measurement
characteristic and sends a small pulse-rate payload over BLE. This is historical functionality only
and is not part of any canonical NHM transport contract.

## Credentials

The supplied firmware contained hardcoded network (Wi-Fi) credentials in source. Those credentials
are **not** reproduced anywhere in this repository, in this document, or in any report generated by
this task. No secret value from that firmware is committed, logged, or printed.

**Security recommendation**: the exposed Wi-Fi network password should be rotated. This is a
routine hygiene recommendation, not confirmation that the credential has been abused.
